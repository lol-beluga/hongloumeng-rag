# 长时间查证任务的设计

一个多步考证可能经历搜索、阅读、再次搜索和生成结论。它比普通 HTTP 查询慢，还会消耗模型额度。这里需要解决的问题是：提交能否及时返回、重复请求会不会多执行一次、工作积压如何限制，以及中断后能否找回进度。

## 一次请求经过什么

1. `JobController` 校验问题长度、模式和 `Idempotency-Key`。
2. `JobService` 查询是否已有对应请求；已有且内容一致就返回原任务。
3. 申请并发容量，向 H2 插入 `QUEUED` 任务。插入事务提交后，才向线程池派发。
4. 工作线程通过带状态和执行次数条件的 SQL 把任务改成 `RUNNING`。
5. `PythonWorker` 用 `ProcessBuilder` 启动 Python，通过标准输入输出交换 JSON。
6. Python 只检索原文，或使用与 Java 相同的任务编号启动 / 恢复 Agent。
7. Java 保存完成或暂停结果；浏览器定时查询并展示。

## 关键机制与实现

| 机制 | 对应代码与行为 |
| --- | --- |
| Spring MVC、参数校验 | `JobController` 使用 REST 接口、`@Valid`、长度和模式校验 |
| IoC / 依赖注入 | Controller、Service、Repository 通过构造方法注入；执行器抽象为 `WorkerRunner`，测试替换真实 Python 进程 |
| 事务与代理 | `JobRepository.insert()` 使用 `@Transactional`；Service 调用独立 Repository Bean，在事务提交后派发工作 |
| SQL 唯一约束与索引 | `request_key` 唯一约束处理并发重复提交；时间索引支持最近任务查询 |
| JUC 线程池 | 固定工作线程、`ArrayBlockingQueue` 和明确的拒绝策略 |
| Semaphore | 在写入数据库前预留容量；任务结束或派发失败时释放 |
| 乐观并发控制 | `WHERE id=? AND attempt=? AND status=...` 条件更新，依据受影响行数判断是否抢到执行权 |
| 幂等与重试 | 同请求编号返回同任务；显式重试复用任务编号，增加执行次数 |
| 生命周期与进程管理 | `@PreDestroy` 停止执行器；进程超时强制结束，重启时识别未完成任务 |
| 自动化测试 | JUnit、内存 H2、真实 HTTP 测试，分别验证并发和接口行为 |

## 为什么线程池必须有界

模型调用慢时，无界排队只会让更多请求堆在内存里。这里默认2个工作线程和8个排队位置，容量满了直接返回 `429`，调用方可以稍后使用相同请求编号再试。

线程池使用 `AbortPolicy`，避免让提交 HTTP 请求的线程执行耗时查证。`CallerRunsPolicy` 虽然能减慢提交速度，但在这个接口里会让用户原本应该很快收到的任务编号迟迟不返回。

Semaphore 管的是准入：先拿到容量再写任务，正常的队列满不会产生一条永远无人执行的记录。线程池有界队列仍负责执行侧的容量限制。关闭服务或短暂调度竞争仍可能导致派发失败，这时会记录失败并返回 `503`。

配置应根据单进程内存、任务耗时和接口额度调整。当前默认值用于个人工具，没有做过生产负载压测，也没有吞吐量提升的结论。

## 为什么不能只用“先查后插”防重复

两个线程可能同时查不到记录，然后同时插入。查询只是快速返回路径，正确性最终依赖数据库的 `UNIQUE(request_key)`。只有一个插入成功，另一个收到唯一约束冲突后，重新读取已经存在的任务。

发生冲突时还要比较问题与模式。同一个请求编号被用于不同内容时返回 `409`，否则会让调用方误以为新问题已被接收。

幂等范围是“同一请求编号创建同一个任务”。相同问题换一个编号可以创建新任务；这不是按问题内容做永久缓存。在极端竞争下，并发重放可能先遇到容量不足而返回 `429`，调用方仍应沿用原编号重试。

## 事务解决什么，没有解决什么

`insert()` 的插入和读取在短事务内完成。工作派发发生在 Repository 代理方法返回之后，所以工作线程能读取已提交记录。没有把模型调用放进事务里，避免长时间占用连接与数据库锁。

Spring 的代理事务要求调用经过代理。这里由 Service 调用另一个 Bean 的公开方法；如果把事务方法改成同类内部自调用，默认代理模式下不会按预期启用新的事务边界。

数据库提交与内存入队之间仍存在中断窗口，事务不能把这两个动作变成一个原子操作。当前的处理是：启动时将遗留的 `QUEUED` / `RUNNING` 标记为 `INTERRUPTED`，让用户决定是否恢复。若要实现服务重启后自动可靠派发，需要数据库任务领取机制或 Outbox + 消息队列，并继续处理消费者幂等。

## 为什么重试还要加执行次数

状态本身不够区分两轮执行。任务失败后再执行，`attempt` 从1增加到2；第一轮迟到的结果不能覆盖第二轮状态。

领取、重试与完成更新都包含预期状态和 `attempt` 条件。这相当于在业务状态上做比较后更新；更新行数为0时说明条件已经改变。这里没有使用 JPA 的 `@Version`，也没有把 Java 内存里的 `synchronized` 当作数据库状态保护。

重试只允许从 `FAILED`、`PAUSED`、`INTERRUPTED` 进入 `QUEUED`。已完成或仍在执行的任务返回 `409`。这一设计避免普通重复点击同时推进同一个任务。

## 为什么有 H2 和 SQLite 两个存储

H2 保存任务提交与交付信息：请求编号、状态、执行次数、最终结果和时间。SQLite 保存 Python Agent 的中间过程：已找原文、消息、待执行工具、调用预算和事件。

两边共用任务编号，但没有跨库事务。例如 Python 已完成并保存，Java 还没拿到结果就停止了；用户重试时，Python 读取已完成检查点并返回，不必重新调用模型。

如果中断发生在模型返回后、Python 保存前，重试仍可能再次调用模型。请求幂等、检查点恢复与“模型只计费一次”是不同层面，当前无法承诺最后一点。

H2 便于直接启动，当前是单实例个人工具。迁移到 MySQL 时，需要调整驱动、连接配置、建表语句与迁移流程，并重新验证事务隔离和唯一键冲突行为。当前实现不能称为已经使用了 MySQL 或 Redis。

## 为什么通过子进程连接 Python

检索和 Agent 已经在 Python 中实现，把它们作为受限执行进程可以复用现有逻辑，并对整次任务设置超时。输入以 JSON 写入标准输入，不拼接成 Shell 命令；问题中的引号、空格和换行不会变成命令。

代价是每个任务需要启动进程并加载索引。当前并发小，这个实现便于运行和排查；如果启动开销成为瓶颈，可以让 Python 常驻，通过 HTTP / RPC 提交任务。那时需要补充跨服务鉴权、超时、重试和幂等协议，不能只把函数调用替换成网络请求。
